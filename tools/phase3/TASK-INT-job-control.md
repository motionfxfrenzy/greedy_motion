## Step 2: chaos tests, locally, on the real stack
Add `tools/phase2/job-control/chaos.mjs` (reusing `scripts/plates-e2e/lib.mjs`) with these scenarios, each with explicit assertions and measured times:
1. **Kill the worker mid-render** (`docker kill` the plate worker while a scene is drawing): the lease lapses, pg-boss retries, a restarted worker completes it as attempt 2, no duplicate publication, no double charge for a final render (use a billed render job).
2. **Cut the control link** (`docker pause` or stop `plate-api` for 20 s while a worker holds a lease, then resume): the worker's calls are retried with bounded backoff, the lease is either kept or cleanly lost, nothing is published twice, the job finishes.
3. **Restart the API during a long poll and during a finish call**: the worker reconnects, a finish whose answer was lost returns `duplicate` on retry and the output stays the worker's.
4. **Duplicate completion** (send `finish` twice, and `finish` from a stale attempt): only the current attempt commits.
5. **Many waiting workers**: start 6 worker containers (scale `plate-worker`), queue 10 scenes from 2 projects, and check that all complete, each exactly once, and that **total Postgres client connections from the workers stay at zero** (count with `pg_stat_activity` by `application_name` or client address) while the API's own connections stay within its pool budget.
6. **HyperFrames render through job control**: a project with a non-plate look, rendered through `POST /v1/projects/:id/render`, must finish to a valid MP4 with the worker holding no database credentials. If the plates-e2e stack cannot render a HyperFrames film (missing template or font), say exactly what is missing and prove the queue path with the closest honest test; do not claim a pass you did not observe.
