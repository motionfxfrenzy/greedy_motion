Draw once, play smooth

The scene code draws every frame on the viewer's computer. This page shows how the stored copies of those frames look, and the full plan for fast drawing, smooth 30 fps playback with sound, and replays that never redraw.

Part 2 · The plan

What we change, and in what order

Your rules for this work: the scene code draws on the viewer's computer; the viewer may wait while it draws; playback must be a smooth 30 fps with voice, music and sound effects in step; once drawn, a scene replays without drawing again; quality never drops; the model's drawing is never restricted.

Showing a frame that is already drawn takes 0.07 ms, so playback itself is never the problem; drawing is. Today the preview plays at 15 fps, frees each frame after showing it (so a replay redraws), lets sound run on while the picture waits, and falls back to the server MP4 when a scene would take more than 20 s to prepare.

Why drawing is slow: 83 to 90 % of each frame is spent in one engine function that builds the crayon scribble fill. For every few pixels of a shape it asks "is this point inside the outline?", and each answer walks every edge of an outline of hundreds of points, about 70 fills per frame. The hand-written scenes you run locally reuse their fills because their shapes stay still; the model's scenes move and re-draw shapes each frame, so the work is real and has to get cheaper.

1 · Faster engine, identical pictures

Building nowNo quality change
What
The engine's "inside the outline?" test first rejects points outside the shape's box, then checks only the outline edges at that point's height, from a small index built once per outline. Same comparisons, same arithmetic, same answer.
Measured
148 → 28.5 ms, 268 → 43.9, 186 → 39.9, 35 → 18.7 ms per frame; byte-identical frames at 640 × 360 and 1920 × 1080. The final render on AWS gets the same 5 to 6× speed-up.
Proof required
The engine's golden hashes unchanged; 200,000 random points against 300 shapes give the same answer as the old test; frame fingerprints of every style identical at both sizes; a test where scene code edits an outline in place.
Rollout
Each scene bundle carries its own engine copy, so existing scenes are re-bundled from their saved code with no model call; their cached preview clips are redrawn once.

3 · Buffer like a video, sound in step

NextNo quality change
What
Start after a short buffer (about 1 s, longer for slow scenes so they rarely pause), keep 2 to 3 s drawn ahead, and if playback reaches the last drawn frame, pause with a buffering indicator and resume when ready. Never show a wrong frame.
Sound
One clock drives picture, voiceover, music and sound effects. Buffering pauses all of them at the same instant and resumes them together; sound effects are scheduled from the clock, not from timers.
MP4
The 20 s limit goes. The server MP4 stays only for browsers that cannot run the live player, or a drawing worker that keeps crashing.

4 · Draw once, replay forever

NextLossless: no quality change
What
Each frame is saved the moment the code draws it, keyed by the scene's exact revision. When every frame is saved, the scene is complete: replay, loop and seek read the saved frames and never run the code again. A comment makes a new revision; only that scene redraws.
Where
On the viewer's disk in browser storage, so long films fit on small devices; only the 2 to 3 s playback buffer lives in memory (about 55 to 80 MB). Saving runs in a second worker; loading a frame takes about 6 ms.
Format
Lossy WebP at 0.4 by default (about 34 KB per frame, 15 MB for a 15 s film). The viewer can pick Low 0.2 (20 KB, 9 MB), Standard 0.4 or High 0.6 (48 KB, 21 MB) in the step-3 options bar; saving a frame takes 19 to 24 ms in a second worker and loading one 2.4 to 3.6 ms, so every option replays smoothly at 30 fps. The first play always shows the exact drawn frames; only replays use the stored copy. Changing the setting starts a background job on the viewer's computer: playback, scrubbing and clicking keep using the existing copies with no wait, while the job redraws frames with the scene code (raising the quality) or re-saves the copies (lowering it), nearest the playhead first, then the rest of the film. Each frame switches to the new quality the moment it is ready; a scrub moves the job's focus to the new position; playback always gets the CPU first; the job resumes after a reload. The final render is unaffected: the AWS worker runs the code itself at 1920 × 1080, 30 fps.

5 · Draw ahead in the background

After 4No quality change
What
While the viewer reads the storyboard or watches one scene, the next scenes keep drawing and saving, one at a time, so most of the film is ready before they press play.

How each step is checked before it ships

  • Pixel identity: engine golden hashes, the random-point test, per-style fingerprints at two sizes, and fingerprints of replayed frames against freshly drawn ones (lossless).
  • Playback: a headless Chrome run of the four staging crayon scenes at 30 fps: zero wrong frames, every buffering pause matched by an audio pause, picture and voice within one frame of each other after resume.
  • Storage: replay after reload draws nothing; a comment redraws only its scene; storage stays under the cap.
  • All frontend, backend and engine suites; then the crayon film on staging in Chrome, timed.

Who does what, and alongside what

  1. Change 1: a Sonnet agent, in its own worktree, running now. I review, re-run the proofs and commit.
  2. Changes 2 and 3 together, then 4: the live player and the plates step-3 page, in a second worktree; they touch different files from change 1.
  3. Re-bundle existing scenes with the new engine, then deploy to staging and time the crayon film.
  4. Argon's HyperFrames edit fix (phase 4a) continues in parallel; it touches none of these files.

Risks and open points

  • Storage: at the 0.4 default a 15 s film needs about 15 MB and a 60 s film about 60 MB (lossless would be 221 and 880 MB). Storage is capped per site, about 500 MB, oldest films cleared first; if a phone refuses the space, the scene simply redraws on replay.
  • Only desktop Chrome is measured. Safari and Firefox still use the MP4 until someone runs the device check on them.
  • Change 1 assumes scene code does not edit an outline in place after drawing with it; a guard rebuilds the index when the outline's length or end points change.
  • Decided: stored frames are lossy WebP 0.4 by default, with Low 0.2 and High 0.6 as viewer options.
