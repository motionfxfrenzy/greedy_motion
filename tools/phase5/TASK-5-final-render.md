# Task for the coding agent: phase 5, the final render draws exactly what the user previewed (frozen manifest, worker-side drawing, no silent repair)

You work for a manager (Claude) who reviews everything you produce and re-runs your key checks. Read this whole file first. Do what it says, in the order written. If a rule blocks you, stop that part and say so in the report; never work around a rule.

## Why
Today a plate film's final render and the companion exports (`backend/src/plates/exports.ts`, `prepareFilm` in `backend/src/render/service.ts`) are a thin wrapper: they ask the queues to draw any missing scene clip (`requestDraws`, `draw_aspects`, `plate-render` jobs) and then the render job idles, polling, until every scene is `drawn` (`resolveClips` in `worker/src/plates.mjs`). Known problems (see `docs/LIVE_SCENES_PLAN.md` sections 9, 21, 24 and the 2c report): (1) what is rendered is not guaranteed to be what the user previewed, because a comment edit or a storyboard change while the render waits changes the clips it assembles or fails it with "scenes were changed"; (2) the render job holds a worker slot while it idles; (3) `draw_aspects` never expires, so after one render every later comment revision is drawn to an MP4 on AWS, defeating "a comment costs no render"; (4) a scene that fails verification at export time is silently repaired. The product decision (plan section 9): **the final render draws exactly the frozen set of revisions the user last previewed, the worker draws what is missing itself, a scene that fails verification stops the render before any frame is drawn, costs nothing, and goes back to the preview as "needs fix" with a repair revision.**

## What to build

### 1. The frozen export manifest (schema 2), built when the user clicks Render
- At Render (and for each companion-export request), the backend freezes the film: for every scene of the aspect, the **current revision**: `variantId`, `gen`, `rev`, `bundleDigest`, `bundleKey` (the bundle object in object storage), `paramsDigest`, `params`, frames, start frame; plus the timing, voice and music object keys **with their digests**, subtitle settings, cues, sound effects, aspect, size, fps, watermark flag, `engineDigest`, `fontSetDigest`, and the film signature. Store it immutably in object storage under a content-addressed key (hash of the canonical JSON); the render job's input references that key. Never mutate a stored manifest.
- If some scenes are still being authored when the user clicks, the backend (in the planning stage of the render job) waits for authoring to finish (bounded wait, progress events as today), then freezes; if authoring fails or exhausts its repair budget, the render fails **without charge** with the scene named.
- Keep schema 1 readable for jobs already in flight (the worker accepts both; schema 1 keeps its old path until it drains; write a test).

### 2. The worker draws, verifies and caches, itself (no waiting on other queues)
Rewrite `renderPlateFilmJob` and the companion-export path to work only from the frozen manifest:
1. **Download and verify every bundle first**: object exists, content hash equals the manifest's digest (use the same hash definition the backend and the browser use; note that the engine's `bundleSha` is the hash of the HTML plus a trailing NUL byte, see `docs/phase2/2b-report.md`; reuse the existing helper, do not invent a third definition), the bundle passes the existing in-browser verification the worker already does in `handlePlateRender` (no page errors, meta matches, frames 0, middle and last drawn twice are identical, no network). Verification of **all** scenes happens before **any** scene is drawn.
2. **If any scene fails verification: stop.** Fail the job with a non-retriable, typed error naming the scene (`scene_needs_fix`), **before drawing a frame**, with **no charge** (the existing refund path, see 4), and hand the scene to the existing bounded repair path (`plate.sendBackForRepair` through the control operations) so it returns to preview as a repair revision. **No repair or redraw of different code ever happens inside the render.**
3. **Clip cache by digest**: look up each scene's clip by `(bundleDigest, engineDigest, fontSetDigest, size)` in a new table (migration; check the next free number, `021` or later; idempotent) such as `app.plate_clips` with the object key, frames and meta; reuse a hit (this is also the clip the preview fallback and any earlier render produced: make the preview clip path `handlePlateRender` write the same content-addressed entry, so nothing is drawn twice). Misses are drawn **by the render job itself**, with the existing software-GL path and bounded concurrency (`PLATE_CONCURRENCY`), uploaded to a content-addressed key, and recorded through a new control operation (fenced by the job attempt). A retry after a worker crash reuses every scene already drawn.
4. **Software-GL self-check**: before drawing, record the renderer string and **refuse to draw** (typed error `gpu_path_detected`, retriable on another worker) if it is not a software renderer (SwiftShader, llvmpipe or equivalent), so previews and exports never silently differ because of a GPU path. Unit-test the decision function with fake renderer strings; the real stack reports SwiftShader.
5. Then assemble exactly as today (voice, music, effects, subtitles, watermark) from the manifest's own object keys and digests (verify the audio digests too).
6. The render job no longer idles waiting for `plate-render` jobs: **no `requestDraws`, no `draw_aspects`, no `plate-render` message is needed for a final render or an export.** Remove the calls to `requestDraws` from `prepareFilm` and `requestExport`, stop reading `draw_aspects` in `commitBundle`, the reconciler and `demand.idle`, and make the column unused (leave it in the schema; add a migration comment; do not drop data). The preview fallback (`/clip-request`) and the `PLATE_LIVE_FORCE_OFF` rollback keep using `plate-render`.
7. Worker slot: a render job that is drawing is working, not idle; report its stages through the existing progress events. Record in the report how many CPU-bound draws one worker task runs in parallel and the memory use observed.

### 3. A comment or storyboard change while a render runs
Nothing a user does after clicking Render changes that render. Prove it: edit and re-author a scene during a render (the render still produces the frozen revision; the new revision is previewable afterwards), and change the storyboard text during a render (no "scenes were changed" failure; the old film completes). A second Render click after edits freezes a **new** manifest and produces a new film.

### 4. Billing
Understand the current flow (`spendTokens` at the click, `refundSpend` on failure) and make it correct and tested for the new flow: charged once per accepted click; **idempotent per click** (an `Idempotency-Key` header or an equivalent client-supplied key on `POST /v1/projects/:id/render`: the same key returns the same job and one charge; document the behaviour and keep requests without a key working as today); refunded exactly once on every failure that is not the user's cancellation (scene verification failure, authoring exhausted, retries exhausted, worker error), never refunded twice, never charged for a render that fails before drawing; settled (kept) on success. Companion exports stay free of tokens as today.
